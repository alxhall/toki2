### Important ambiguity

The upstream `save_timer` service creates the provider entry **before** marking the active timer finished in the repository. Timeout, 500, or loss of the HTTP response cannot safely be treated as proof that no entry was created. The deployed OpenAPI document is not itself evidence of a transaction boundary or idempotency guarantee.

## Local slow-save reproduction

`python3 tasks/repro_slow_save.py target/release/toki-tui` uses a loopback HTTP stub, a throwaway config/session directory, and a draining PTY; it never contacts production or stores terminal output. With the original 0.4.0 release build, after the stub received `PUT /time-tracking/timer` and held the response, sending `q` **did not exit within 0.5 s**. Releasing the response let the TUI exit normally (status 0). This confirms an event-loop input stall during a slow save on Linux; it does **not** explain which Windows process held 25 GB or prove save idempotency. The script is a manual reproduction fixture, not yet a pass/fail CI regression test.

The harness now supports `--mode slow-save|slow-refresh|server-error|lost-response`; all four modes reproduced ignored input while the stub held the response, then exited normally after release. `lost-response` deliberately drops the HTTP connection **after receiving the request**, so the client must not interpret the subsequent error as proof no entry was written. The optional `--require-responsive` switch turns the PTY harness into an expected-to-fail regression check on 0.4.0: it exited nonzero with `TUI ignored quit input while save was pending`. It is not wired into CI until the off-loop behavior is implemented. For a safe native-Windows starting point, `tasks/windows-memory-sample.ps1` samples either `toki-tui-windows.exe` (the released asset) or `toki-tui.exe`, plus Windows Terminal, OpenConsole, conhost and wslhost separately every 10 s for up to 15 min; it stops sampling on ≥1 GiB growth or ≥2 GiB private memory and warns the tester to close the TUI manually. Linux cannot validate the PowerShell script or reproduce native Windows behavior.

## Save guard and local off-loop verification in progress

The TUI writes a small `pending-save.json` record **before** attempting a save: account ID, server timer start, attempt timestamp and requested mode. It contains neither note text nor credentials. Creation is exclusive and synced; an existing or malformed record blocks another save. The input loop now spawns **one** save worker and **at most one** history refresh worker; each save/restart/read has an explicit 30-second deadline. It blocks timer mutations while an attempt is in flight or unresolved, but supports quit and read-only history navigation; quitting retains the marker and prints a warning. A confirmed response clears the record; 500/lost-response retains the original timer/note and unresolved record, without automatic replay. On restart, the UI warns and blocks subsequent saves.

**Local evidence:** 65 TUI tests pass in an isolated Cargo target directory, including create-before-network, duplicate guard, server 500, lost response, confirmed-save/failed-restart, refusal of manual recovery and exclusive process locking. The loopback PTY harness now passes `--require-responsive` in all five modes (`slow-save`, `slow-refresh`, `lost-response`, `server-error`, `deferred-history`): q exits in <0.5 s with a response held; repeated save keys send only one PUT. It checks marker presence after quit (absent after a confirmed save), and for unresolved modes relaunches the TUI with the same isolated config: the marker survives, and a second save is blocked. `deferred-history` confirms a history request made during an in-flight save is fetched after the uncertain result. A read-only code review identified two stale-history risks; the event loop now defers that history request and aborts older history reads before entry edits/deletions. Ordinary Clippy passes with only the recorded pre-existing warnings. After a user decision, `toki-tui resolve-save` now acquires an exclusive per-config OS lock, verifies the same account, reads the current server timer and up to 30 days of entries with bounded requests, then asks for an exact interactive confirmation before clearing *only* the matching local record. Wrong input/EOF leaves it intact; unavailable server/auth fails closed. The lost-response PTY case uses its fake account to verify refusal, exact confirmation, no replay and local-only clearing. The user must close all TUI copies, including older builds that do not participate in the lock, and independently verify an inconclusive history in the web app. **Do not deploy or use this branch against production yet:** actual provider save semantics, manual Windows smoke tests and native-Windows memory attribution remain open.
